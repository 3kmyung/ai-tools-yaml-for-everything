# 긴 회의 전사하기

## 개요

이 예제는 Microsoft의 `VibeVoice-ASR`를 사용해 회의, 인터뷰, 팟캐스트 같은 긴 녹음을
전사합니다. `VibeVoice-ASR`는 외부에서 청크로 나눈 창(window) 단위가 아니라 최대 한 시간
분량의 오디오를 한 번의 패스로 처리하도록 만들어진 비스트리밍 음성-텍스트 체크포인트입니다.
이 예제를 위해 새로 만든 화면은 세그먼트 목록 위에 화자별로 색이 입혀진 타임라인을 얹은
형태입니다. 오디오 파일 하나를 떨어뜨리면 `{ text, start_time, end_time, speaker_id }`
형태의 세그먼트 집합이 만들어지고, 화면은 각 화자를 타임라인과 목록 양쪽에서 동일한 색으로
표시해, 대본을 한 줄도 읽지 않고도 누가 언제 말했는지 볼 수 있게 합니다. 핫워드 입력란은
모델이 잘못 알아들을 수 있는 도메인 용어를 `context_info`로 전달합니다.

## 준비사항 및 필수 요구사항

- `model-compose`가 설치되어 `PATH`에서 사용 가능해야 합니다.
- 16GB 이상의 RAM. 7B급 체크포인트에는 GPU를 강력히 권장합니다. CPU만으로도 동작하지만
  느립니다.
- 최초 실행 시 체크포인트 다운로드와 캐시를 위해 약 20GB의 여유 디스크 공간이 필요합니다.
- 계정, 토큰, 외부 서비스는 필요하지 않습니다 — 모델은 다운로드가 끝나면 완전히 오프라인으로
  동작하며, 유일한 입력은 페이지에 떨어뜨린 로컬 오디오 파일입니다.

## 환경 구성

이 예제는 `.env` 변수를 전혀 읽지 않습니다. 워크플로우가 노출하는 모든 설정 —
`context_info`, 디코딩 파라미터 — 은 페이지에서 전달되거나 `model-compose.yml`에 이미
정해진 기본값을 그대로 사용합니다.

## 실행 방법

```bash
cd releases/speaker-diarization-vibevoice
model-compose up
```

웹 UI를 `http://localhost:8081`에서 엽니다. 첫 실행은 체크포인트를 다운로드하므로 인터넷
속도에 따라 몇 분이 걸릴 수 있습니다. 이후 실행은 로컬 캐시에서 바로 시작됩니다.

## API

정적 페이지는 curl 예제나 CLI가 아니라 `run_workflow`를 통한 WebSocket 클라이언트입니다.
페이지는 다음과 같은 입력으로 `transcribe-meeting` 워크플로우를 호출합니다.

```json
{
  "audio": "<streamed file>",
  "context_info": "Microsoft,VibeVoice"
}
```

완료되면 다음과 같은 출력을 받습니다.

```json
{
  "transcription": [
    { "text": "Let's start with the quarterly numbers.", "start_time": 0.0, "end_time": 2.8, "speaker_id": 0 }
  ]
}
```

이는 이 저장소 자체의 `speech-to-text-vibevoice` README가 문서화하는 형태입니다.
Transformers 모델 문서는 같은 모델에 대해 `processor.decode(...,
return_format="parsed")`가 대신 `{ Start, End, Speaker, Content }`를 반환한다고 보여줍니다.
`model-compose`가 실제로 페이지에 어떤 형태를 넘기는지는 실제 `model-compose up` 실행이
결과를 내놓기 전까지는 확정되지 않습니다 — 아래 "동작 원리"를 참고하세요. 페이지는 둘 중
어느 형태도 직접 읽지 않습니다: `ui/src/segments.js`가 내보내는 단 하나의 어댑터
`segmentsFromResponse`가 어느 쪽이 도착하든 렌더링 코드가 보기 전에
`{ text, startTime, endTime, speakerId }`로 정규화합니다. 그래서 실제 형태가 확정되는 날,
세그먼트를 그리는 모든 모듈이 아니라 함수 하나만 바뀌면 됩니다.

## 입력 파라미터

| 파라미터 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| `audio` | audio | 예 | — | 전사할 녹음 파일 (MP3, WAV, FLAC 등) |
| `context_info` | text | 아니오 | — | 인식을 도메인 용어 쪽으로 유도하는 쉼표 구분 핫워드, 예: `Microsoft,VibeVoice` |

## 동작 원리

`VibeVoice-ASR`의 음향 토크나이저는 7.5Hz 프레임 레이트로 동작하며, 이 덕분에 64K 토큰
언어 모델이 약 한 시간 분량의 오디오를 하나의 컨텍스트 창에 담을 수 있습니다.
"단일 패스"는 토크나이저가 아니라 파이프라인을 설명하는 표현입니다: 내부적으로 모델은
여전히 오디오를 60초 단위 세그먼트로 나누고 세그먼트 사이의 합성곱 상태(convolution
state)를 캐시하지만, 어떤 청크 경계도 컨텍스트를 리셋하지 않습니다 — 상태가 그대로
이어지므로 언어 모델은 전체 녹음을 독립적으로 판단된 여러 창의 연속이 아니라 하나의 연속된
구간으로 봅니다. 이는 Whisper의 30초 창과는 종류가 다른 숫자입니다: Whisper의 한계는
인코더가 학습된 길이에 고정된 아키텍처 상수인 반면, VibeVoice의 60초 내부 청크 크기는
문서가 제한된 하드웨어에서 낮추라고 권하는 런타임 메모리 파라미터입니다 — 결과를 바꾸는
값이었다면 사용자가 조정할 수 있게 열어두지 않았을 것입니다. 두 숫자 모두 하나의 컨텍스트
창이 담을 수 있는 오디오 양을 결정하는 프레임 레이트 자체는 건드리지 않습니다.

화자별로 색이 입혀진 타임라인은 바로 이 하나의 연속된 패스를 눈에 보이게 만드는
장치입니다: 모델이 반환하는 모든 세그먼트에는 `speaker_id`가 붙어 있고, 화면은 이를
실제 시작·종료 시각에 맞춰 배치된, 가로로 스크롤되는 색 블록 띠로 바꿉니다. 옆의 목록에서도
각 세그먼트의 행이 같은 색을 갖습니다. 화자 이름을 텍스트 안에 적어 넣은 단순한 스크롤
대본 화면이었다면 같은 데이터를 담고 있어도 대화의 모양 — 누가 누구의 말을 끊는지, 각
발언이 얼마나 이어지는지, 침묵이 어디에 있는지 — 은 보여주지 못했을 것입니다. 타임라인의
모든 색은 손으로 고른 팔레트가 아니라, 단 하나의 `--accent` 디자인 토큰에 CSS
`hue-rotate` 필터를 적용해 만들어집니다. 그래서 이 화면은 디자인 시스템 자체의 색상
범위를 벗어나는 새 색을 만들어내지 않고도 화자를 구분해 보여줍니다.
