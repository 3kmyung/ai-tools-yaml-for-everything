# 转录一场长会议

## 概述

本示例使用微软的 `VibeVoice-ASR` 转录一段较长的录音——会议、访谈或播客。
`VibeVoice-ASR` 是一个非流式的语音转文本检查点,设计目标是一次性处理最长约一小时的音频,
而不是依赖外部分块的窗口。为此专门设计的界面,是在分段列表上方叠加一条按说话人着色的时间轴:
拖入一个音频文件,就会得到一组 `{ text, start_time, end_time, speaker_id }` 形式的分段,
界面会在时间轴和列表两处用同一种颜色标出每位说话人,让读者不必读一行文字就能看出谁在什么
时候说话。热词输入框会把模型可能听错的领域词汇通过 `context_info` 传给模型。

## 准备工作与前提条件

- 已安装 `model-compose` 并可在 `PATH` 中找到。
- 16GB 以上内存;对于这个 7B 级别的检查点,强烈建议使用 GPU。仅用 CPU 也能运行,但速度较慢。
- 首次运行需要约 20GB 的可用磁盘空间,用于下载和缓存检查点。
- 不需要任何账号、令牌或外部服务——模型下载完成后完全离线运行,唯一的输入就是拖放到页面里的
  本地音频文件。

## 环境配置

本示例不读取任何 `.env` 变量。工作流暴露的所有设置——`context_info`、解码参数——要么由页面
传入,要么直接使用 `model-compose.yml` 中已经写好的默认值。

## 运行方法

```bash
cd examples/showcase/speaker-diarization-vibevoice
model-compose up
```

在 `http://localhost:8081` 打开网页界面。首次运行会下载检查点,视网络速度可能需要几分钟;
之后的运行会直接从本地缓存启动。

## API

这个静态页面是通过 `run_workflow` 进行通信的 WebSocket 客户端,而不是命令行工具或 curl
示例。页面会用如下输入调用 `transcribe-meeting` 工作流:

```json
{
  "audio": "<streamed file>",
  "context_info": "Microsoft,VibeVoice"
}
```

完成后会收到如下输出:

```json
{
  "transcription": [
    { "text": "Let's start with the quarterly numbers.", "start_time": 0.0, "end_time": 2.8, "speaker_id": 0 }
  ]
}
```

这正是本仓库自己的 `speech-to-text-vibevoice` README 所记录的形状。而 Transformers 的模型
文档则显示,同一个模型的 `processor.decode(..., return_format="parsed")` 返回的是
`{ Start, End, Speaker, Content }`。`model-compose` 实际会把哪种形状交给页面,在真正执行一次
`model-compose up` 产出结果之前并不确定——见下文"工作原理"。页面本身不会直接读取任何一种
原始形状:`ui/src/segments.js` 导出的唯一一个适配函数 `segmentsFromResponse` 会把无论到达的
是哪种形状,都归一化成 `{ text, startTime, endTime, speakerId }`,再交给渲染代码。这样等真实
形状确定下来的那一天,需要修改的只是这一个函数,而不是每一个绘制分段的模块。

## 输入参数

| 参数 | 类型 | 是否必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `audio` | audio | 是 | — | 待转录的录音文件(MP3、WAV、FLAC 等) |
| `context_info` | text | 否 | — | 用逗号分隔的热词,用于让识别偏向领域词汇,例如 `Microsoft,VibeVoice` |

## 工作原理

`VibeVoice-ASR` 的声学分词器以 7.5Hz 的帧率运行,这正是一个 64K token 的语言模型能够把大约
一小时音频装进单个上下文窗口的原因。"单次处理"描述的是流水线,而不是分词器本身:模型内部
仍然会把音频切成 60 秒一段的片段,并在各段之间缓存卷积状态,但没有任何分段边界会重置上下文——
状态会一直延续下去,因此语言模型看到的是整段录音连成的一个整体,而不是一系列各自独立判断的
窗口。这和 Whisper 的 30 秒窗口是完全不同性质的数字:Whisper 的限制是一个由编码器训练时长
决定的架构常数,而 VibeVoice 60 秒的内部分块大小是一个运行时的显存参数,文档甚至建议在硬件
受限时把它调低——如果这个值会改变结果,就不可能开放给用户调整。这两个数字都不会影响决定单个
上下文窗口能装下多少音频的帧率本身。

按说话人着色的时间轴,正是让这"单次连续处理"变得可见的地方:模型返回的每个分段都带有
`speaker_id`,界面把它们变成一条可以横向滚动的彩色色块带,按真实的起止时间排列;旁边列表中
每个分段所在的行,也使用同一种颜色。如果只是一个把说话人姓名写在文字里的普通滚动文本转录
界面,虽然包含同样的数据,却无法展现对话本身的形状——谁打断了谁、每次发言持续多久、沉默出现
在哪里。时间轴上的每一种颜色,都不是手工挑选的调色板,而是在唯一的 `--accent` 设计令牌上
应用 CSS 的 `hue-rotate` 滤镜派生出来的。因此这个界面能够区分不同说话人,同时不必在设计系统
自身的色彩范围之外发明新的颜色。
