# Model Showcase Skills — Design

## Overview

Three Claude Code skills plus one example that exercises them. The goal is a repeatable
daily routine: pick a model, ship a small `model-compose` example with a purpose-built
web GUI that demonstrates what makes the model distinctive, measure it on three
machines, and publish a report and a short post.

The three skills live in `~/.claude/skills/` — not in this repository. `.gitignore:187`
excludes `.claude/`, and this repository is a fork whose upstream should not carry
personal workflow tooling. The skills describe how their author works; the repository
carries only their output.

| Artifact | Kind | Location |
|---|---|---|
| `ui-house-style` | skill | `~/.claude/skills/ui-house-style/` |
| `model-showcase` | skill | `~/.claude/skills/model-showcase/` |
| `model-report` | skill | `~/.claude/skills/model-report/` |
| `transcribe-long-meeting` | example | `examples/showcase/transcribe-long-meeting/` |

The example is generated by `model-showcase`, never hand-written. It is both the first
deliverable and the test case that drives the two skills to maturity.

## Goals

- Codify the house frontend style that already exists in
  `examples/media-processing/youtube-to-playlist-video/ui/` as a rules document, so that
  every generated GUI shares its philosophy, structure, conventions, and usability
  without shipping a copy-paste starter kit.
- Make one model's example reproducible end to end from a model name, with human
  judgement required at exactly two points: what to demonstrate, and whether the real
  run worked.
- Produce a report and an X post carrying measured numbers from three machines, with
  measurement conditions stated, and no number that lacks a source.
- Fix the accessibility and naming defects in the reference UI as part of writing the
  rules, rather than propagating them into every generated example.

## Non-goals (YAGNI)

- A shared UI package under `examples/_shared/`. Each example stays self-contained and
  runnable on its own; `controller.webui.static_dir` points at a directory inside the
  example.
- A starter kit of copyable files inside `ui-house-style`. The skill is rules plus one
  verbatim token block, because input and output shapes differ per model and a fixed
  scaffold cannot absorb that.
- Deploying a hosted demo. The published link is the GitHub example path; readers clone
  and run `model-compose up`.
- Dark mode. `base.css` declares `color-scheme: light` and the palette stays single-mode.
- Automated benchmark collection over SSH or cloud instances. All three machines are
  physically available and runs are started by hand.

## Build order

```
1. Write ui-house-style                 (extracted from youtube-to-playlist-video/ui/)
2. Write model-showcase                 (calls ui-house-style for the frontend)
3. Loop:
     model-showcase generates examples/showcase/transcribe-long-meeting from scratch
     → fixture + test.html + headless screenshot
     → dissatisfied: edit the skills, delete the example, regenerate
4. model-compose up — one real run, end to end
5. Write model-report; benchmark on three machines; publish
```

The example is never hand-patched. Hand-patching measures the patch, not the skill, and
the loop stops converging. Anything unsatisfactory is fixed in a skill's prose and the
example is regenerated whole.

### Two verification loops

| Loop | Verifies | Mechanism | Cost |
|---|---|---|---|
| Fast, run dozens of times | generated `ui/` code, layout, UX | `ui/test.html` + fixture JSON, served by `assets/serve.mjs`, captured with headless Chrome | seconds |
| Slow, run once or twice | compose wiring, real transcription | `model-compose up` with real audio | tens of minutes |

The fast loop needs no model and no GPU. `assets/serve.mjs` exists because Python's
`http.server` serves `.js` with a MIME type that blocks ES module loading; a Node static
server with correct types does not.

The fixture is hand-written from the model card's example output on the first pass, then
replaced with one saved real run after step 4. From then on the fast loop renders real
data.

### Acceptance check per iteration

Place the generated `ui/` beside `youtube-to-playlist-video/ui/` and confirm:

- `base.css` tokens are identical in name and scale.
- One file, one concern.
- No framework, no build step: plain ES modules under `<script type="module">`.
- Function bodies split into declaration / work / return paragraphs by blank lines.
- Icons come from an open-source set, not hand-drawn path data.
- The screenshot reads as the same family as the playlist UI (human judgement).

## Skill C: `ui-house-style`

```
~/.claude/skills/ui-house-style/
├── SKILL.md
└── references/
    ├── tokens.md
    ├── layout.md
    ├── components.md
    ├── css-patterns.md
    ├── js-patterns.md
    └── streaming.md
```

`SKILL.md` stays at one page: when to invoke, the four-step process, and the
self-critique checklist. Rules live in `references/` and are read on demand.

### Process in SKILL.md

1. **Tokens** — read `tokens.md`, lay down `base.css` unchanged.
2. **Layout** — decide what the list is and what the workspace is, map onto the
   three-region skeleton in `layout.md`.
3. **Components** — assemble from `components.md` first. A new widget only when no
   existing one fits.
4. **Self-critique** — re-read the written code against the checklist. New colour
   invented? `box-shadow` used? State toggled from JS? Comments left behind? Fix.

Step 4 is borrowed from Anthropic's official `frontend-design` skill, which is the only
researched open-source skill worth taking anything from — and its core premise (choose a
fresh distinctive aesthetic per subject) is the opposite of what is wanted here, so only
its plan/build/critique spine carries over. Catalogue skills (UI/UX Pro Max, Taste,
Impeccable) are noise against a fixed house style, and the Tailwind/shadcn/Framer Motion
families are irrelevant to a zero-framework codebase.

### Rule form: ban, replacement, reason

Every rule is written as three lines:

```
✗ box-shadow
→ Express depth with --background-panel and --radius-lg.
Why: this UI has no light-source metaphor. Layers are surface brightness only.
```

A ban without a replacement gets routed around; a ban without a reason gets rationalised
away as "this case is different". Both halves are load-bearing.

### `tokens.md`

Carries `base.css` verbatim as a code block, then:

- Do not use values outside the scale. Spacing is `--space-1..5`, type is
  `--text-sm/base/lg`, corners are `--radius-sm/base/lg/full`, transitions are
  `--duration-fast/base/slow`. The scale is the contract even where a value is currently
  unused.
- The one exception is component-intrinsic dimensions — thumbnail `2.5rem`, icon button
  `1.75rem`, slider thumb `0.875rem`. These are physical sizes, not reusable steps, and
  must not be tokenised.
- Do not invent colours.

**Palette change: split the accent.** The current `--accent: #007ffb` measures 3.61:1
against `--background: #f7f7f8` by WCAG relative luminance, below the 4.5:1 AA threshold
for normal text. It is used as text in `footer a` and `#warning`, and as the text colour
on the filled primary button (same 3.61:1, at `font-weight: 500` / 14px, which does not
qualify as large text). The fill itself is fine; only text use fails.

```css
--accent: #007ffb;        /* fills, borders, focus rings */
--accent-text: #0a6ed9;   /* link text, warning text, text over accent fills */
```

`#0a6ed9` measures 4.62:1 and stays in the same blue family.

**`--disabled` is not for content.** `#a9abb0` measures 2.15:1 against the background.
Disabled controls are exempt under WCAG, but `#hint` ("Add a track to begin") is real
instructional text and is not. Instructional text uses `--text-caption` (4.63:1).

### `css-patterns.md`

Bans, each with replacement and reason:

- `box-shadow` for elevation → `--background-panel` + `--radius-lg`.
- Decorative `linear-gradient` → flat surfaces. The one scrim on `.thumbnail-frame::after`
  is the whole budget.
- JS class toggling for state → `body:has(#control[data-value="x"])` and CSS reads the
  DOM directly, as `layout.css` already does for aspect ratios.
- A popover positioning library → the native `popover` attribute, `:popover-open`,
  `@starting-style`, and `transition ... allow-discrete`.
- Scroll event listeners → `@property` + `animation-timeline: scroll(self block|inline)`,
  as the mask-image scroll fade already does.
- Per-component hover and focus declarations → add the selector to the existing `:is(...)`
  list.
- Styling by ID in `components.css` → style by class. A component is reusable by
  definition and an ID is not.
- Domain nouns in `components.css` → `.item`, `.item-label`, `.item-remove`.

`layout.css` keeps its ID selectors. The page regions it styles (`#settings`,
`#workspace`, `#log`, `#hint`) are singletons belonging to the fixed three-region
skeleton, and that skeleton does not change per example. The ban is about components
leaking into per-example identity, not about IDs as such.

The last two are the drift engine and are worth stating with evidence. `components.css`
currently carries ten ID selectors, and commit `846fe3a8`'s own message records the cost:
renaming the example required changing "the Render button's DOM id **and the CSS that
selects it**". `.track` / `.track-label` / `.remove-track` had to become `.camera` in the
intercutting example for the same reason. These are the largest contributors to the
177-line divergence between the two examples' `components.css`.

Renames: `#render-playlist` → `.action-primary`, `#add-track` → `.action-add`,
`#warning` → `.caption-warning`, `#log > span` → `.status-message`.

**Focus indication.** One rule generates the whole table:

> Focus recolours the outermost line the element already has, to `--accent`. An element
> with no such line, or whose line is already `--accent`, gets an inward ring instead.

| Element | Existing outer line | Focus treatment |
|---|---|---|
| `.field-line`, `.color-picker-hex` | `border-bottom 1px` | underline → accent |
| `.color-picker-swatch` | `border 1px transparent` | border → accent |
| `.dropdown` | `border 1px var(--border)` | border → accent |
| `.item` | `border 1px var(--border)` | border → accent |
| `.action-add` | `border 1px var(--accent)` | inward ring |
| `.action-primary` | none; background is accent | inward ring in `--background` |
| `.item-remove`, `.revert-field` | none | inward ring |
| `.dropdown-option` | none | inward ring |
| `footer a` | none | `text-decoration-thickness: 2px` |

```css
/* base.css — default. Anything that does not supply its own indicator gets this. */
:is(button, a, input, select):focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: -2px;
}

/* components.css — an element with its own indicator turns the default off. */
:is(.dropdown, .item, .color-picker-swatch):focus-visible {
  outline: none;
  border-color: var(--accent);
}

/* Only where the background is already accent does the ring invert. */
.action-primary:focus-visible {
  outline-color: var(--background);
  outline-offset: -3px;
}
```

`outline: 0` and `outline: none` are permitted only inside a block that supplies a
replacement indicator in the same declaration. The current global reset at `base.css:56`
is banned: it removes the ring for every interactive element and leaves a 6%
`color-mix` background tint in its place, which is not a visible focus indicator.

**Reduced motion.** The reference UI has no `prefers-reduced-motion` handling at all,
while transitioning every interactive element and animating dropdowns, the footer, and
the scroll fades:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: .01ms !important;
  }
}
```

This is safe for the scroll-fade animations: with the animation collapsed, the custom
properties settle at their `to` values (`--scroll-fade-start: var(--space-5)`,
`--scroll-fade-end: 0px`), which leaves the mask opaque rather than hiding content.

**Responsive.** The reference UI has zero `@media` and zero `@container` rules, and
`main`'s two-column grid has a hard floor of `13rem + 16rem = 464px`, below which a
desktop layout scrolls sideways. This matters beyond principle: the X post needs a
portrait video, which needs a working mobile layout.

| Target | Mechanism | Reason |
|---|---|---|
| Page skeleton (`header` / `main` / `footer`) | `@media (width < …)` | the viewport itself is the condition |
| Reusable components (fields, dropdowns, list items) | `@container` | they must work in a narrow slot and a wide one |

```
>= 900px    unchanged. main: [list clamp(13rem, 22vw, 20rem) | workspace]

600–900px   main collapses to one column; the list lies down as a horizontal rail
            above the workspace.
            grid-template-columns: 1fr;
            grid-template-rows: auto minmax(0, 1fr);

< 600px     list and workspace become alternating views; selecting an item switches
            to the workspace. The header settings row already scrolls horizontally
            with a mask fade and stays as is. The primary action moves from header
            to footer for thumb reach.
```

Breakpoints are not tokenised — custom properties cannot be used in `@media`
conditions. The two numbers are fixed in this document and repeated in `layout.md`.

`.field-body:has(.thumbnail)` is already doing container adaptation by proxy; it moves to
`container-type: inline-size` plus `@container (width < 20rem)`.

### `js-patterns.md`

- ES modules, named exports only. No `export default`. No `class` — `createX()` factories
  returning object literals.
- No `innerHTML`, no template-string DOM construction. `document.createElement` plus
  `Object.assign`; updates through `replaceChildren()`.
- Hide with the `hidden` attribute, never `style.display`.
- No abbreviated names. `identifier`, `sequence`, `parseFailure` — not `i`, `ctx`, `el`, `e`.
- No comments.
- Function bodies read as declaration / work / return, separated by blank lines.
- One file, one concern. Past 100 lines, look for the split.

### `components.md`

Markup and behaviour specs for the dropdown, field, button, list item, popover and status
bar, written against the renamed class-based selectors.

Icons:

> Do not draw icon path data. Take the SVG from [Lucide](https://lucide.dev) (ISC) and
> copy only the path data into the `ICONS` map. Stroke-based 16×16, `stroke-width: 1`,
> `fill: none`, `aria-hidden="true"`. Do not mix in a filled set.

The current `icons.js` hand-draws five icons (`"M4.5 4.5L11.5 11.5M11.5 4.5L4.5 11.5"`
and friends), which is exactly what this rule replaces.

### `layout.md`

The three-region skeleton is fixed. `header` carries a horizontally scrolling settings
row and the primary action at its right. `main` is a list column of
`clamp(13rem, 22vw, 20rem)` beside a workspace. `footer` carries the log and hides itself
via `:not(:has(...))` with a `@starting-style` slide-in when empty. Only the inside of
`main` changes per example.

### `streaming.md`

Both reference examples are batch renderers, so the house style has no streaming
vocabulary yet. Streaming is not "one more component" — it is a layout that changes along
a time axis, and batch rules applied to it actively harm: a `translate` entry animation on
items arriving ten per second induces motion sickness.

Output streaming:

1. A growing list gets a fixed-height container and scrolls inside it. The page does not
   grow. This is the existing `#track-scroller` language: `overflow-y: auto`,
   `min-height: 0`, mask fade.
2. Auto-scroll only while pinned to the bottom. When the reader scrolls up, tracking stops.
3. Unconfirmed (partial) text is `--text-caption`; confirmed (final) is `--text`. No new
   token. Transition on `--duration-fast`.
4. No `translate` on item entry. `@starting-style` may animate opacity only.
5. Changing numbers — timecodes, counters — use `font-variant-numeric: tabular-nums`, as
   `.color-picker-readout` already does. This is layout-shift prevention, not decoration.
6. No DOM update per chunk. Batch to one update per frame with `requestAnimationFrame`.
7. The streaming region is `aria-live="polite"` with `aria-atomic="false"`, and only
   confirmed units are appended. Swapping partial text every frame is unusable with a
   screen reader.
8. Progress and cancel reuse the existing `showProgress({ onCancel })` language in the
   footer. Do not build a second progress UI.

Input streaming:

9. Request microphone permission only immediately after a user gesture.
10. No red dot for recording state. Use an `--accent` pulse or a level meter — the
    no-new-colour rule applies here too.
11. A level meter is a div painted with tokens, not `<meter>`, whose native rendering
    cannot be controlled across browsers.
12. Stop changes the primary button's label. Do not add a second button; the right side
    of the header holds one action.
13. Play PCM streams through WebAudio. Do not swap `<audio src>` per chunk.

Common:

14. Streaming animations — pulses, blinking cursors — stop entirely under
    `prefers-reduced-motion`. State is then carried by colour alone.

### Six steps, two human gates

| Step | Who | Output |
|---|---|---|
| 1. Research | automatic | variants, sizes, licence, I/O mode, hardware, distinguishing mechanism |
| 2. Map | automatic | which of the 35 model tasks, which driver, which existing example is the base |
| 3. **Demo angle** | **human** | one killer property, three screens that would show it, pick one |
| 4. Generate | automatic | compose + `ui/` (invokes `ui-house-style`) + fixture + READMEs + index entry |
| 5. Fast verify | automatic | `serve.mjs` → headless screenshot → self-critique checklist |
| 6. **Real run** | **human** | `model-compose up` once |

Step 3 is why this skill exists. Everything else is mechanical; deciding what to show is
not. For VibeVoice-ASR the killer property is single-pass hour-long audio via a 7.5 Hz
continuous tokeniser, and three defensible angles are: a speaker-coloured timeline, a
side-by-side against Whisper, and a hotwords-on/hotwords-off contrast. Same model, three
completely different screens.

### `research.md`

Source order: Hugging Face model card → project GitHub README → arXiv paper → Transformers
model doc.

Required fields: variants and parameter counts, licence, input and output shape,
**streaming or batch (or both)**, hardware floor, the one mechanism that distinguishes the
model, and any withdrawal or restriction history.

Two gates:

- **Licence gate.** Anything other than MIT or Apache-2.0 stops and asks. VibeVoice's own
  history is the reason: the TTS 1.5B and 7B weights were pulled on 2025-09-04 after
  Microsoft found out-of-scope use, and the repository came back on 2025-09-05 without the
  TTS code. Building an example on withdrawn weights wastes a day and publishing about
  them invites trouble.
- **No guessing.** Parameter counts, context lengths and benchmark figures require a
  source URL. Without one the field is marked `needs verification` and settled by the step
  6 run. The VibeVoice-ASR checkpoint is listed as 7B on GitHub and 9B on the Hugging Face
  card; a number like that must not reach the report unresolved.

The I/O mode field feeds step 3 directly: when a model family has both a batch and a
streaming checkpoint, the demo angles split along that line before anything else.
`VibeVoice-ASR` and `VibeVoice-ASR-Streaming` produce entirely different screens.

### `compose.md`

- Copy the nearest existing example's component block rather than writing one from
  scratch.
- `controller.webui.driver` is `static` with `static_dir: ./ui`. Gradio is not used in a
  showcase example.
- Every workflow that the UI calls needs an `id`; the UI reaches it through
  `run_workflow` over the WebSocket endpoint.

**Do not rewrite `ui/src/websocket-client.js`.** Copy it verbatim from
`examples/media-processing/youtube-to-playlist-video/ui/src/websocket-client.js`. Its
`stream_pull` backpressure, post-reconnect task resubscription and binary chunk framing
are the model-compose WebSocket protocol, not design decisions, and regenerating 305 lines
of protocol code from prose will produce bugs. This is the one file the rules-only
approach explicitly does not cover; it is B's responsibility, not C's.

File drop needs no new infrastructure: `streamFile(file)` in that client already returns
the `__variable__` stream descriptor the server pulls from.

### Directory naming

`examples/showcase/` holds `find-person-scenes`, `upscale-video`, `analyze-disk-usage`,
`make-inspiring-quote-voice`, `echo-server` and `vibevoice-realtime-tts`. Four of six are
verb-object; the model-named one is the outlier. The rule is verb-object, because an
example sells a capability rather than a model.

### `readme.md`

Three READMEs per example — `README.md`, `README.ko.md`, `README.zh-cn.md` — matching the
structure documented in `examples/README.md`.

`examples/README.md` carries a one-line index entry per showcase example at lines 177–181.
An example missing from that index is effectively invisible, so adding the entry is on the
step 4 checklist.

### `verify.md`

`node serve.mjs` serves the example's `ui/`; headless Chrome loads `ui/test.html`, which
reads the fixture and injects it straight into the render functions — no WebSocket stub.
Chrome is invoked in self-exiting `--screenshot` mode. Never kill Chrome by image name;
that closes the user's real browser.

## Example A: `examples/showcase/transcribe-long-meeting`

Generated by `model-showcase`, not written by hand.

- **Model:** `microsoft/VibeVoice-ASR`, MIT, batch. Chosen over the TTS side because the
  TTS weights are withdrawn, the licence is clean, and the distinguishing mechanism is
  visible on screen.
- **Base:** `examples/model-tasks/speech-to-text-vibevoice` — its component block carries
  over almost unchanged; `webui.driver` moves from `gradio` to `static` and the workflow
  gains an `id`.
- **Input:** local file drop only. No YouTube URL, no sample bundle — zero dependencies,
  fully reproducible, and the cleanest thing for the skill to template from.
- **Screen:** speaker-coloured timeline, segment list, hotword input feeding
  `context_info`.
- **Output shape:** `{ text, start_time, end_time, speaker_id }[]`, which is also the
  fixture schema.

New modules beyond the house set: `dropzone.js`, `timeline.js`, `segments.js`,
`hotwords.js`.

## Skill D: `model-report`

```
~/.claude/skills/model-report/
├── SKILL.md
├── references/
│   ├── benchmark.md
│   ├── report.md
│   └── social.md
└── assets/
    ├── capture.mjs
    └── bench-hw.py

benchmarks/<example-name>/
├── scenario.md
├── data/
└── results/{macbook,rtx4090,dgx-spark}.json
```

### Reusing the existing harness

`benchmarks/common/metrics.py` already provides `MetricsCollector` and `SystemSample`
against a three-event contract (`runtime.ready`, `pipeline.first_output`,
`pipeline.done`). That contract and the metric computation carry over. The axis changes:
the existing benchmarks compare frameworks (model-compose against LangGraph and
LangChain), while this compares hardware.

**Gap to close: no GPU memory tracking.** `SystemSample` records `rss_bytes`,
`cpu_percent` and `num_threads` only. For a three-machine comparison this is disqualifying
— on the 4090 the weights live in VRAM separate from RSS, while the Mac and the Spark use
unified memory where the two overlap. Comparing RSS alone would report that the Mac uses
far more memory, which is a measurement artefact.

`SystemSample` gains `vram_bytes`, read from `torch.cuda.max_memory_allocated()` on CUDA
(including the Spark's GB10) and `torch.mps.current_allocated_memory()` on MPS.

### Metrics

| Metric | Definition | Purpose |
|---|---|---|
| Cold start | `model-compose up` → `runtime.ready` | checkpoint load plus venv or docker build; the largest hardware spread |
| TTFO | `first_output − ready` | existing contract |
| E2E | `done − ready` | existing contract |
| RTF | `E2E ÷ audio duration` | the ASR standard; below 1 is faster than real time. This is the number that goes in the post |
| Peak VRAM | new | does this run on this machine at all |
| Peak RSS | existing | overlaps VRAM on unified-memory machines; must be annotated |
| Output identity | diff of the three transcripts | does precision change the result |

### The precision trap

`precision: auto` resolves to bfloat16 on CUDA, float16 on MPS and float32 on CPU. The Mac
and the 4090 are therefore not running the same numerics, and reporting "Mac 15s, 4090 4s"
without saying so is a false comparison.

Two tables:

| | Matched conditions (`float16` forced) | Real-world conditions (`auto`) |
|---|---|---|
| Purpose | hardware comparison | what you get if you install it |
| Placement | body | appendix |

Every figure in the report carries its precision, batch setting and sample length.

No expectation about relative DGX Spark performance is written down before it is measured.
The same no-guessing rule that governs B's research step governs D's numbers.

### Report structure

```
1. One-line definition    what this model is
2. What is different      one or two architectural points, with a diagram
3. What was built         demo description plus screenshot or video
4. Performance            three-machine table with conditions, plus two or three
                          sentences of interpretation
5. Limits                 what it cannot do, what to watch for, licence constraints
6. Links                  GitHub example path, model card, paper
```

Section 4's interpretation is mandatory. A bare table goes unread; one sentence such as
"the 4090 leads at RTF 0.08, but the Mac's 0.4 is still 2.5× real time, so a laptop is
practical" is what carries the result.

### Media capture

| Artefact | Method |
|---|---|
| Screenshot | headless Chrome `--screenshot`, self-exiting. Never `taskkill` by image name |
| Video | CDP `Page.startScreencast`, frames piped to ffmpeg |
| Portrait video | the `< 600px` mobile layout from C at viewport `390×844` |

The portrait video is the concrete reason C carries responsive rules.

### Social post

X only, Korean only. One template: 280 characters, extended as a thread, with the link
placed in a reply so the first post's reach is not reduced.

Four required elements: one line on the model, exactly one performance number (usually RTF
or "an hour in N minutes"), the demo media, and the GitHub example link.

## Decisions on record

- **Rules document, not a starter kit** (C). Chosen for flexibility across input and
  output shapes. The known cost is drift — `status.js`, `icons.js` and `base.css` are
  currently byte-identical between the two reference examples while `websocket-client.js`
  has diverged by 82 lines and `components.css` by 177. The mitigations are the
  no-ID-styling and no-domain-noun rules, which remove the two largest mechanical causes,
  and moving the protocol client out of C into B as a verbatim copy.
- **Interactive generation, not fully automatic** (B). Judging what a model should
  demonstrate is not automatable; rework costs more than the conversation.
- **GitHub example path as the published link.** No hosting, no deployment.
- **Skills in `~/.claude/skills/`, not the repository.** `.gitignore:187` excludes
  `.claude/`, and the upstream fork should not carry personal tooling.
