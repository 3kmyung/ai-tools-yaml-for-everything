## 메모리 판독

`vram.peak_bytes`에 담기는 값은 컴포넌트(Component) 런타임(Runtime)이 도는 위치에 따라 다르다.

| 컴포넌트 런타임 | 가속기 | 담기는 것 |
| :---: | :---: | --- |
| 러너(Runner) 프로세스(Process) 안 | CUDA, MPS(Metal Performance Shaders) | 러너 자신의 `torch` 판독 |
| 자식 프로세스 | CUDA | `nvidia-smi` 샘플의 피크, 러너 프로세스 트리 합산 → Windows처럼 프로세스별 메모리를 안 주는 드라이버는 `null` |
| 자식 프로세스 | MPS | `null` → `torch.mps`는 러너 프로세스만 보고 `nvidia-smi`가 없다 |
| 컨테이너(Container) | 전부 | 러너 프로세스분만 → 컨테이너 자신의 수치를 따로 읽는다 |

상주 메모리 피크를 기기의 "메모리"로 보고하지 않는다. 비디오 메모리 피크와 나란히 두고, 통합 메모리 기기에는 같은 바이트를 두 번 셌다고 붙인다. 안 그러면 그 기기만 훨씬 많이 쓰는 것처럼 보인다.

## 가속기가 연산을 지원하지 않는 기기

메모리가 아니라 백엔드(Backend)가 막는 경우다. MPS의 `Output channels > 65536 not supported`처럼 커널(Kernel)이 없으면 양자화(Quantization)로도 안 풀린다.

| 회피 | 그 행이 재는 것 |
| :---: | --- |
| 같은 기기의 CPU 실행 | 가속기를 안 쓴 값이라 다른 행과 비교 불가 |
| 다른 추론 스택(Stack)의 변환본 | 다른 구현이라 기기 간 간극이 아니다 |
| 막힌 서브모듈(Submodule)만 CPU로 내리는 설정 | 그 기기 → 행이 성립한다 |

앞의 둘은 성립하지 않는다. 세 번째는 모델(Model)을 그 기기의 가속기에 그대로 올린 채 커널이 없는 한 조각만 옮기므로, 나머지 연산이 전부 가속기에서 도는 그 기기의 값이다. 그래서 `--option <컴포넌트>.<설정>=<값>`으로 주어 조건에 남기고, 배포된 compose 파일은 고치지 않는다.

아래 "가중치가 안 올라가는 기기"의 오프로드(Offload) 행과 헷갈리지 않는다. 거기는 들어갈 자리가 없어 옮기는 용량 회피라 무엇을 옮길지 고를 수 없고, 여기는 커널이 없는 한 조각만 지목하는 기능 회피다.

셋 다 못 쓰면 그 기기는 미측정이며, 막은 연산의 오류 문구를 그대로 적고, "느리다"로 적지 않는다.

## 데이터셋을 다 못 도는 기기

돌기는 도는데 `dataset.sample_count`를 다 채울 시간이 없는 경우다. 얼마나 걸릴지는 추정하지 않고 한 건을 실제로 재서 곱한다.

```bash
execute --machine $M --detach -- python -B $R/measure.py ... --item-limit 1 \
  --output-directory .benchmark/pilot/$M --results-directory .benchmark/pilot
```

파일럿(Pilot)은 캐시(Cache)를 덥히는 실행을 겸하므로 따로 워밍업(Warmup)을 돌리지 않는다. 나온 `item_end_to_end_seconds.median`에 `sample_count`를 곱한 값과 그 한 건의 실측치를 사람에게 보이고, 이 기기에 쓸 시간 예산을 묻는다. `N`은 `예산 ÷ 실측치`를 내림한 값이고, `sample_count` 이상이면 끊지 않고 전부 돌린다.

| `N` | 할 일 |
| :---: | --- |
| `1` 이상 | `--item-limit N`으로 기록 실행 → 부분 표본 행 |
| `0` | 한 건도 예산에 안 들어간다 → 미측정, `reason`에 실측 한 건의 초와 곱한 총시간을 적는다 |

`--item-limit`은 같은 `inputs.jsonl`의 앞에서부터 `N`건을 돌린다. 입력 파일을 따로 만들지 않으므로 `inputs_sha256`이 다른 기기와 같고, 표본이 갈렸다는 이유로 거절당하지 않는다.

| 규칙 | 어기면 |
| --- | --- |
| 부분 표본 행은 `machine_distance`의 기준 기기가 될 수 없다 | 다른 기기가 댈 항목이 모자란다 |
| 보고에 그 행의 `item_count`를 함께 싣는다 | 20건으로 잰 중앙값과 3건으로 잰 중앙값이 같은 열에서 같은 무게로 읽힌다 |
| `p95`는 `max`와 나란히 읽는다 | 표본이 작으면 `p95`가 최댓값과 붙는다 → 두 값이 거의 같은 행은 꼬리를 못 잰 행이다 |
| 예산을 안 물어보고 `N`을 정하지 않는다 | 몇 시간을 쓸지는 기기를 쓰는 사람이 정한다 |

## 가중치가 안 올라가는 기기

가중치(Weight)를 못 올리면 먼저 그 크기를 구한다. 크기는 기기나 내려받기 없이 아래 값으로 판단한다.

| 값 | 읽는 곳 |
| :---: | --- |
| 모듈(Module)별 바이트 | `model.safetensors.index.json`의 텐서(Tensor) 이름과 샤드(Shard) 헤더(Header)의 바이트 오프셋(Offset)을 이름 앞 두 마디로 묶어 합산 |
| 양자화 후 크기 | 백본(Backbone) 바이트 × (목표 비트 ÷ 원본 비트) |
| 토큰(Token)당 키-값 캐시(Cache) | `config.json`에서 `2 × layers × key_value_heads × head_dimension × 원소 바이트` |

| 가중치와 키-값 캐시 | 할 일 |
| :---: | --- |
| 기기 메모리보다 작다 | 용량 문제가 아니다 → 남의 프로세스는 중지하지 않고, 오류 문구와 크기를 사람에게 보이며 비운 뒤 다시 잴지 묻는다 |
| 기기 메모리보다 크다 | 그래도 이 기기를 재는 설정이 있는지 사람에게 묻는다 |

| 설정 | 그 행이 재는 것 |
| :---: | --- |
| 양자화 | 그 기기 → 행이 성립한다 |
| 일부를 시스템 메모리로 오프로드(Offload) | 오프로드 → 행이 성립하지 않는다 |

끝내 못 재면 그 기기는 미측정이며, 크기 때문이면 `reason`에 "N기가바이트에 안 들어간다"를, 아니면 오류 문구를 적는다.

| 하면 | 그 대신 |
| --- | --- |
| 총 크기만 보고 기기가 작다고 결론짓는다 | 전정밀도로 남는 모듈이 만드는 바닥을 먼저 구한다 → 17기가바이트의 5분의 1이 양자화 불가면 4비트 바닥은 4.25가 아니라 6.8기가바이트다 |
| 라이브러리(Library) 하나가 이 가속기를 지원하지 않는다고 양자화 빌드(Build)가 없다고 결론짓는다 | 모델(Model)의 허브(Hub) 조직과 커뮤니티 변환 조직을 먼저 찾아본다 |
| PyTorch로 안 올라가니 다른 추론 스택으로 재서 같은 표에 넣는다 | 그 기기를 미측정으로 남긴다 → 커널과 메모리 배치가 달라 기기 간 간극이 아니다 |
